뉴스 수집기 앱의 새 기능 개발을 아래 순서대로 진행한다. 단계를 건너뛰지 말고, 사용자 확인이 필요한 곳에서는 답을 받을 때까지 다음 단계로 넘어가지 않는다.

브랜치 이름 인자: `$ARGUMENTS`

## 1. 현재 상태 확인

`git status`와 `git branch --show-current`로 현재 브랜치와 작업 트리 상태를 확인한다.

- **main이 아닌 경우:** 현재 브랜치 이름과 함께 경고하고, main으로 이동할지 물어본다.
  - 동의하면 `git switch main`을 실행한다.
  - 거부하면 워크플로를 중단한다.
- **커밋되지 않은 변경이 있는 경우:** 변경 파일을 보여주고 어떻게 처리할지 물어본다. 사용자가 지시하지 않은 stash, 되돌리기, 커밋은 하지 않는다.

## 2. 새 브랜치 생성

- **`$ARGUMENTS`가 있는 경우:** 그 값을 브랜치 이름으로 쓴다.
- **`$ARGUMENTS`가 비어 있는 경우:** 어떤 기능을 개발할 것인지 물어보고, 답변을 바탕으로 영어 소문자-하이픈 형식(예: `category-filter`)의 브랜치 이름을 제안한다. 사용자가 확인하면 그 이름을 쓴다.

같은 이름의 브랜치가 이미 있으면 알리고 다른 이름을 받는다. 그다음 `git switch -c <브랜치-이름>`으로 브랜치를 만든다.

## 3. 개발 시작 안내

브랜치 생성이 끝나면 **"이제 개발을 시작하세요!"** 라고 안내한다.

`CLAUDE.md`를 읽고 이 프로젝트의 기술 스택과 컨벤션을 짧게 다시 알려준다. 다음 내용을 포함한다.

- 기술 스택
- 명령어 (`npm run dev`, `npm run build`, `npm run lint`)
- UI 작업 전 `ui.md`를 읽는 규칙
- 코드를 쓰기 전 `node_modules/next/dist/docs/`를 확인하는 규칙
- 아키텍처 핵심 제약 (단일 사용자, 인증 필수, 기사당 번역·요약 1회, 비밀값 비노출 등)

마지막으로, 개발이 끝나면 `완료` 또는 `done`이라고 입력하라고 알려주고 여기서 멈춘다.

## 4. 완료 후 커밋과 병합

이 단계는 사용자가 `완료` 또는 `done`이라고 입력했을 때만 진행한다. 그 전까지는 개발 요청을 평소처럼 처리하고, 커밋이나 병합은 하지 않는다.

1. `git status`와 `git diff`, 그리고 브랜치에 이미 커밋이 있으면 `git log main..HEAD`로 변경 내용을 확인한다.
2. 변경된 파일 목록을 보여준다. `.env` 같은 비밀값 파일이 포함되어 있으면 커밋 대상에서 빼고 알린다.
3. 변경 내용을 바탕으로 커밋 메시지를 제안한다. 이 저장소의 형식대로 한국어 한 줄로 쓴다. (예: `Notion MCP로 뉴스 저장 버튼 추가`)
4. 사용자가 확인하면 관련 파일을 스테이징하고 커밋한다. 메시지 수정을 요청하면 반영해서 다시 확인받는다.
5. main으로 이동해 병합한다. 이 저장소의 병합 커밋 형식을 따른다.

   ```
   git switch main
   git merge --no-ff <브랜치-이름> -m "Merge branch '<브랜치-이름>': <작업 설명>"
   ```

충돌이 나면 임의로 해결하지 말고, 충돌 파일을 보여주고 어떻게 할지 물어본다. 사용자가 요청하지 않으면 push나 브랜치 삭제는 하지 않는다.

## 5. 작업 요약

병합이 끝나면 다음을 요약해서 보여준다.

- 브랜치 이름과 병합 커밋 해시
- 구현한 내용
- 변경된 파일 (`git diff --stat HEAD^1 HEAD` 기준)
- 사용자가 확인해야 할 후속 작업이 있다면 그 내용 (환경변수 추가, DB 마이그레이션 등)
